# H1 - the 0.1.0 horizon - what must exist before AMUSE gets an avatar-root component

## 1. Question and bounded scope

> What must AMUSE complete before it can ship a script that a user puts on the
> root of an avatar, if the only optimization is alpha separation?

Alpha separation moves the triangles of an AlphaTest or AlphaBlend material that
are proven visually opaque onto an appended submesh. The appended submesh carries
an AMUSE-generated canonical opaque material. The purpose is less overdraw.

This note records the gaps. It does not design any of them. It does not change
production code. Each gap gets a name, evidence, and the consequence for a real
avatar. The note also records the recommended order of work and the items that
must stay out of a first release.

Labels: `[SOURCE]` is a fact read in the tree or in pinned upstream source.
`[MEASURED]` is a fact produced by a run in this investigation.
`[INFERENCE]` is a conclusion. `[DECISION]` is a choice this note makes.
`[DECISION NEEDED]` is a choice that the controller or the user must make.

## 3. Verdict

The component is the least expensive missing piece. The most expensive missing
piece is coverage.

On a purchased VRChat avatar, AMUSE today optimizes almost nothing, and it tells
the user nothing. `[INFERENCE]` from the gates in section 4. A release that adds
the component first gives the user a control with no observable effect.

The gaps divide into four groups:

- **A** - coverage. These gates decide whether any triangle is admitted.
- **B** - product surface. These are the types and channels a user-facing tool
  needs.
- **C** - value. Nobody has measured that the transformation is a net gain.
- **D** - one stale comment.

## 4. Group A - coverage gaps

All paths in this section are relative to
`<repo-root>/Packages/com.alrauna.amuse/Editor/`.

### 4.1 A1 - the host lifecycle pins use exact string equality

`HostLifecycleCapability.cs:63-67` pins four versions:

| Pin | Value |
|---|---|
| Unity | `2022.3.22f1` |
| NDMF | `1.14.4` |
| VRChat SDK base | `3.10.4` |
| VRChat SDK avatars | `3.10.4` |
| NDMF platform | `nadena.dev.ndmf.vrchat.avatar3` |

The comparison is ordinal equality (`:84-105`). A mismatch stores the refusal and
returns before the avatar is observed
(`Build/AmusePlatformFinishPlugin.cs:329-334`). `[SOURCE]`

The declared dependency is wider than the accepted range. `package.json` requests
`nadena.dev.ndmf` at `>=1.14.4 <2.0.0-a`, and current upstream NDMF is 1.14.8.
`[SOURCE]` A user who installs the package as written can get a version that the
code refuses.

Consequence: one Unity patch release, one NDMF release, or one SDK release turns
the whole feature into a silent no-op.

### 4.2 A2 - locked Poiyomi is refused

`Semantics/Poiyomi/PoiyomiMaterialSemantics.cs:1319-1325` refuses a material when
`evidence.IsLocked` is true. The property is `_ShaderOptimizerEnabled`
(`:1313-1325`). `[SOURCE]`

Most avatars that are sold ship with locked Poiyomi materials. `[INFERENCE]`

An open question makes this worse. Poiyomi locks materials during upload with its
own callback. AMUSE runs in the NDMF `PlatformFinish` phase, inside the NDMF hook
at callback order `-1025`
(`ndmf Editor/VRChat/BuildFrameworkPreprocessHook.cs:64-65`). `[SOURCE]` Whether
Poiyomi locks before or after that point is not established by this note.
`[DECISION NEEDED]` This one fact separates Poiyomi coverage near zero from
Poiyomi coverage across most of the market. It needs a bounded investigation of
its own.

### 4.3 A3 - two shader versions in the world are supported

Shader selection is exact-name only, with four identities
(`Semantics/UnityMaterialSemantics.cs:246-307`). `[SOURCE]`

| Identity | Pinned version | Attestation |
|---|---|---|
| `.poiyomi/Poiyomi Toon` | 9.3.64 | shader GUID, package version, normalized source digest, unlocked state, property schema (`PoiyomiMaterialSemantics.cs:27-33`, `:1296-1388`) |
| `lilToon` | 2.3.4 | name, GUID, pass GUID, `_lilToonVersion == 45`, include-tree digest, shader digest, pass digest (`LilToon/LilToonSourceAttestation.cs:323-343`, `:1243-1332`) |
| `Hidden/lilToonCutout` | 2.3.4 | same shape, own GUIDs and digests (`:352-362`) |
| `Hidden/lilToonTransparent` | 2.3.4 | same shape, own GUIDs and digests (`:363-396`) |

An unsupported shader gives a named refusal and never an exception
(`UnityMaterialSemantics.cs:300-307`, `:104-113`). `[SOURCE]` That behavior is
correct. The coverage effect remains.

### 4.4 A4 - one unattested material refuses the whole renderer

The animation closure admits the current material of every slot and every animated
material-swap value. One unattested material in that set fails the closure with
`UnattestedMaterial`
(`Host/UnityAnimationEvidenceCapture.cs:289-374`). The finish pass consumes the
failure as `MaterialDependencyClosureFailed`
(`Build/AmusePlatformFinishPlugin.cs:502-505`). A null current slot is equally
fatal. `[SOURCE]`

Typical avatars put body, hair, and outfit materials on one renderer.
`[INFERENCE]` One locked or off-version material therefore zeroes the coverage of
its whole renderer.

This is the coverage amplifier. It converts the identity gates of A2 and A3 from
a per-material limit into a per-renderer limit.

### 4.5 A5 - alpha capture needs the Windows 64-bit build target

`Host/UnityAlphaFieldEvidence.cs:514-517` admits only
`BuildTarget.StandaloneWindows64`. The reason is recorded at `:508-513`: the other
standalone members have their own default format tables and were never
characterized, and with another target active the Windows import is not loaded.
`[SOURCE]`

Consequences: no texture-backed proof exists while the editor targets Android, so
Quest avatars get no coverage. A PC user who last built for Quest also gets no
coverage until the target changes back.

### 4.6 A6 - the texture format allowlist

`Host/UnityAlphaFieldEvidence.cs:492-511` admits `RGBA32`, `ARGB32`, `Alpha8`,
`RGB24`, `DXT5`, and `BC7`. `[SOURCE]`

This is the good news in group A. DXT5 and BC7 are the common formats for a
texture that carries alpha. Crunch-compressed formats, DXT1, BC5, BC6H, ASTC, ETC,
and the float formats refuse.

### 4.7 A7 - common sampling states refuse

`Semantics/UnityTextureEvidence.cs` requires:

- a filter mode of Point or Bilinear, so Trilinear refuses (`:185-206`),
- equal U and V wrap modes, each Clamp or Repeat, so Mirror refuses (`:79-84`,
  `:208-223`),
- `mipMapBias == 0` and `anisoLevel <= 1` (`:98-99`). `[SOURCE]`

Anisotropic level 2 or higher is a routine author setting on hair and clothing.
`[INFERENCE]` The refusal is silent.

Two states that are **not** refused deserve a record, because they are the two
that a reader expects: the importer read/write flag is never examined, and the
color space of an alpha request is not relevant. The route is a GPU blit and an
asynchronous readback, not a CPU copy
(`Host/UnityAlphaFieldEvidence.cs:26-37`, `:55-60`). `[SOURCE]`

### 4.8 A8 - lilToon alpha families admit the identity texture transform only

`Semantics/LilToon/LilToonCutoutMaterialSemantics.cs:342-353` and
`LilToonTransparentMaterialSemantics.cs:404-425` refuse a `_MainTex_ST` that is
not `(1,1,0,0)`. `_MainTex_ScrollRotate` must be exactly zero
(`LilToonCutoutMaterialSemantics.cs:262-280`). `[SOURCE]`

Poiyomi has the affine path from PR #42
(`Analysis/AffineUvTransform.cs:33-77`). The lilToon families do not use it.
Tiled hair and skirt UV layouts therefore refuse on both lilToon alpha families.

### 4.9 A9 - Apply-on-Play never mutates

`Build/HostLifecycleCapability.cs:118-120` refuses any build path other than
`NonPlayNdmfBuild`. The path comes from
`EditorApplication.isPlayingOrWillChangePlaymode` (`:138-140`). `[SOURCE]`

The safety choice is defensible. The product effect is that a user cannot see the
result in play mode, only on upload. A user-facing release must state this.

### 4.10 The one path that works today

A renderer whose every slot material and every swap value is attested opaque
`lilToon` 2.3.4 needs no texture evidence at all. That shader's alpha is the
constant 1 (`Semantics/LilToon/LilToonMaterialSemantics.cs:521-547`), so whole
submeshes become `WhollyOpaqueCandidate`
(`Analysis/MeshSeparationPlanner.cs:186-199`). `[SOURCE]`

That is the demonstration case. It is not the product case.

## 5. Group B - product-surface gaps

### 5.1 The upstream minimum

NDMF discovers plugins only by scanning loaded assemblies for the assembly-level
`ExportsPlugin` attribute
(`ndmf Editor/API/Solver/PluginResolver.cs:91-95`). A plugin derives `Plugin<T>`
with a `QualifiedName` and a `Configure` method
(`Editor/API/Fluent/Plugin.cs:38-75`). Work happens in a `Pass<T>`
(`Editor/API/Fluent/Pass.cs:52-69`). `[SOURCE]`

NDMF puts no requirement on the component itself. NDMF 1.14.8 has no
`AvatarTagComponent` class. The current equivalent is a plain `MonoBehaviour`
that implements `INDMFEditorOnly`, which derives `VRC.SDKBase.IEditorOnly` when
the VRChat SDK is present (`Runtime/API/INDMFEditorOnly.cs:13-20`). Component
discovery is each plugin's own query on `BuildContext.AvatarRootObject`.
`[SOURCE]`

NDMF does not remove such a component. Its internal passes remove GameObjects
that carry the `EditorOnly` tag
(`Editor/InternalPasses/RemoveEditorOnlyPass.cs:26-33`) and components with
missing scripts (`RemoveMissingScriptComponents.cs:13-21`). The VRChat SDK
removes `IEditorOnly` components at callback order `-1024`, which NDMF's own
comment attests (`Editor/VRChat/BuildFrameworkPreprocessHook.cs:65`). NDMF also
recommends that a tool destroys its own components when the work is complete
(`docfx~/best-practices.md:11-14`). `[SOURCE]`

The true minimum is four types: the component that implements `IEditorOnly`, a
`Plugin<T>`, one `Pass<T>`, and the `[assembly: ExportsPlugin]` attribute. AMUSE
has the last three (`Build/AmusePlatformFinishPlugin.cs:11`, `:131-140`).
`[SOURCE]`

### 5.2 B1 - there is no runtime assembly

The package holds exactly two assembly definitions. `Editor/` uses
`includePlatforms: ["Editor"]` and references only the two NDMF assemblies.
`Tests/Editor/` is the other. No `Runtime` directory exists. `[SOURCE]`

Unity excludes an editor-only assembly from a player build, so a component in
that assembly cannot ship as a normal avatar component. `[INFERENCE]`

Every studied tool avoids this. NDMF ships its components in
`nadena.dev.ndmf.runtime` with an empty `includePlatforms`, and its changelog
records the rule directly: "`INDMFEditorOnly` needed to be in the runtime
assembly" (`CHANGELOG-PRERELEASE.md:551`). Avatar Optimizer ships
`com.anatawa12.avatar-optimizer.runtime` with an empty `includePlatforms`.
d4rkAvatarOptimizer keeps its component class outside the `UNITY_EDITOR` guard,
and its assembly is named `.Editor` but compiles for all platforms. `[SOURCE]`

### 5.3 B2 - AMUSE runs on every avatar and the user cannot opt in or out

The plugin declares `[RunsOnPlatforms(WellKnownPlatforms.VRChatAvatar30)]`
(`Build/AmusePlatformFinishPlugin.cs:131`) and the renderer loop is unconditional
(`:357-358`). No component, tag, setting, ScriptableObject, or serialized field
exists anywhere in the package. The only gate is the version pin set of A1.
`[SOURCE]`

Both comparable tools key their work off component presence. Avatar Optimizer
queries `AvatarTagComponent` on the avatar root
(`Editor/OptimizerPlugin.cs:65-66`). d4rkAvatarOptimizer queries its own
component and also honors an `ApplyOnUpload` flag
(`Editor/AvatarBuildHook.cs:24`, `Editor/d4rkAvatarOptimizer.cs:39-40`).
`[SOURCE]`

The user's only present controls are to uninstall the package or to fail a
version pin.

### 5.4 B3 - nothing is reported to the user

`ErrorReport` appears in the package only as a capability that must not be null
(`Build/HostLifecycleCapability.cs:37`, `:60`, `:124`, `:153`). No call reports
anything. The package contains no `Debug.Log` call, no `Localizer`, and no editor
window. Per-slot refusals are documented as deliberately unreported
(`Build/AmusePlatformFinishPlugin.cs:479-489`). The result of
`AmuseBuildOperation.Execute` is discarded by its only production caller
(`Build/AlphaSeparationApply.cs:38-42`). `[SOURCE]`

The upstream channel is established and small. A pass calls
`ErrorReport.ReportError(Localizer, ErrorSeverity, key, args)`
(`ndmf Editor/ErrorReporting/ErrorReport.cs:187-191`). A Unity object in `args`
becomes a clickable reference (`InlineError.cs:30-48`). A scope attaches every
error to one object, which is how Avatar Optimizer attributes per-renderer
failures: `using (ErrorReport.WithContextObject(renderer))`
(`ErrorReport.cs:251-268`, `AvatarOptimizer Editor/Processors/MergeBoneProcessor.cs:90`).
The NDMF console opens itself after a build that reported anything
(`Editor/API/BuildContext.cs:556-561`). A severity of `Error` or higher blocks
the upload (`BuildContext.cs:82`, `BuildFrameworkPreprocessHook.cs:91`).
`[SOURCE]`

This gap is not cosmetic. Because of group A, the normal outcome for a user is
that nothing happens. With no report, that outcome is the same as a broken
install.

### 5.5 B4 - no diagnostic survives the build

Every counter and refusal bucket lives in `AmusePlatformFinishState`, which is
NDMF build-context state
(`Build/AmusePlatformFinishPlugin.cs:15-129`). `AlphaSeparationRecords.cs` is
in-memory vocabulary only. The package writes no file. The only file reads are
vendor shader source for attestation. `[SOURCE]`

Every number that AMUSE computes disappears when the build ends.

### 5.6 B5 - generated objects are not registered with NDMF

Material clones come from `new Material(source)`
(`Semantics/LilToon/LilToonOpaqueTarget.cs:270-273`) and mesh clones from
`Object.Instantiate` (`Build/AlphaSeparationPreparation.cs:405-406`). The
`IAssetSaver` that `AmuseBuildOperation.Execute` receives reaches a delegate that
ignores it (`Build/AlphaSeparationApply.cs:41`). The package contains no
`ObjectRegistry.RegisterReplacedObject` call, no `SaveAsset` call, and no
`AssetDatabase` write. `[SOURCE]`

NDMF asks for both duties. `ObjectRegistry.RegisterReplacedObject` keeps later
passes and error reports able to resolve the original object
(`ndmf Editor/API/ObjectRegistry.cs:201-203`). `IAssetSaver.SaveAsset` persists a
generated asset, and NDMF also saves referenced temporaries at the end of a build
(`Editor/API/Serialization/IAssetSaver.cs:15-21`,
`Editor/API/BuildContext.cs:205-268`). `[SOURCE]`

Consequence: another tool, and NDMF's own error UI, cannot map an AMUSE output
back to its source.

### 5.7 B6 - no ordering is declared against any other plugin

`Configure` declares the phase and the internal order of the three AMUSE passes
(`Build/AmusePlatformFinishPlugin.cs:144-164`). The package declares no
`BeforePlugin` and no `AfterPlugin` against another tool. The only such calls are
in AMUSE's own tests, relative to AMUSE. `[SOURCE]`

The upstream facts that matter:

- NDMF phase order is fixed, and `Optimizing` runs before `PlatformFinish`
  (`ndmf Editor/API/Attributes/BuildPhase.cs:96-105`). Avatar Optimizer puts its
  main work in `Optimizing` (`Editor/OptimizerPlugin.cs:60`), so AMUSE already
  runs after it by construction, not by declaration. `[SOURCE]`
- Avatar Optimizer publishes the contract for both directions.
  `BeforePlugin("com.anatawa12.avatar-optimizer")` is the recommended form.
  `AfterPlugin` is possible but "not recommended", and it requires registration
  through their component-information API (`AvatarOptimizer CHANGELOG.md:229-233`).
  `[SOURCE]`
- Ties inside a phase break on the ordinal sort of the plugin type name
  (`ndmf Editor/API/Solver/PluginResolver.cs:21-32`, `:94`). Avatar Optimizer
  deliberately exploits this with an unusual namespace so that it sorts late
  (`Editor/OptimizerPlugin.cs:5-21`). `[SOURCE]`
- d4rkAvatarOptimizer is not an NDMF plugin. It hooks the VRChat SDK directly at
  callback order `-15` when Modular Avatar is installed, and `-1025` otherwise
  (`Editor/AvatarBuildHook.cs:10-18`). `[SOURCE]` With Modular Avatar present it
  therefore runs after the whole NDMF pipeline and can merge the submesh that
  AMUSE appended. No NDMF declaration changes that. `[INFERENCE]`

## 6. Group C - the value is not measured

### 6.1 C1 - there is no profitability policy

`Analysis/MeshSeparationPlanner.cs:176-215` marks a submesh `Split` whenever the
proven-opaque set is neither empty nor complete. There is no triangle threshold,
no area threshold, and no cost model. The apply pass grows `subMeshCount`
(`Build/AlphaSeparationApply.cs:572`). `[SOURCE]`

A split therefore always adds one submesh, which adds one draw call, against an
overdraw gain that nobody has measured. `[INFERENCE]`

The two dispositions are not equal:

| Disposition | Cost | Gain |
|---|---|---|
| `WhollyOpaqueCandidate` | none - the slot swaps its material | full removal of the transparent path for that submesh |
| `Split` | one more submesh and one more draw call | overdraw removal on the proven part only |

A wholly opaque swap is unambiguously good. A split is a real trade that AMUSE
currently always takes.

### 6.2 C2 - every upload pays the full analysis cost

The renderer loop runs before any candidate is known
(`Build/AmusePlatformFinishPlugin.cs:357-429`). Alpha capture reads every mip
level of every admitted texture through a GPU blit and an asynchronous readback,
and one failed level refuses the texture
(`Host/UnityAlphaFieldEvidence.cs:213-249`). `[SOURCE]`

A build with no candidate is correctly bit-identical, because the apply pass
returns before any work (`Build/AlphaSeparationApply.cs:64-68`). `[SOURCE]` The
cost is paid anyway, on every upload, with no way to opt out.

## 7. Group D - one stale comment

`Build/AlphaSeparationRecords.cs:37-43` still lists the transparent family among
the unsupported families. `Build/AlphaSeparationPreparation.cs:465-466` converts
it. The comment is stale from PR #45. `[SOURCE]` One line, no behavior change.

## 8. Dependency-ordered roadmap

Gaps A1, A2, and A4 are independent prerequisites. Group B is one vertical slice.
C1 follows the slice, because it needs a real consumer to measure.

| Order | Item | Kind | Why here |
|---|---|---|---|
| 1 | A1 - relax the version pins to documented minimums | policy change in production code | Least expensive change with the largest coverage effect. Patch equality of Unity, NDMF, and the SDK buys nothing that the shader attestation does not already buy. Until this lands, the component does nothing for a user who is not on one exact configuration |
| 2 | A2 - Poiyomi lock investigation | bounded investigation | One fact decides whether Poiyomi coverage is near zero or covers most of the market. It can also change the phase that AMUSE uses |
| 3 | A4 - per-slot instead of per-renderer attestation closure | design question, then implementation | Removes the amplifier that turns one bad material into a dead renderer. The renderer-wide rule exists because of animated material swaps, so this is a design task and not a refactor |
| 4 | B1, B2, B3, B5, B6 together | one vertical slice | A component with no report is worse than no component. A registered clone is what makes the report resolvable. The ordering declaration is one line inside the same change |
| 5 | C1 - profitability policy | measurement, then policy | Needs the slice above to have a real consumer. Recommended shape to test: always allow a wholly opaque swap, and gate a split behind a threshold |
| 6 | D - the stale comment | cleanup | Can ride with any of the above |

## 9. Out of scope for a first release

These are real, and none of them gates a usable 0.1.0. `[DECISION]`

- A settings user interface beyond one enable control and an exclusion list.
- A preview window in the shape of the d4rkAvatarOptimizer merge preview.
- Localization beyond English.
- Quest and Android support, which needs A5 and its own format characterization.
- A5 itself, beyond a clear refusal message that names the build target.
- A6, A7, and A8 coverage widening. Each is a separate slice with its own proof
  obligations.

## 10. Decisions the controller or the user must make

1. `[DECISION NEEDED]` The Poiyomi lock question of A2. This needs an
   investigation branch of its own before any coverage work on Poiyomi.
2. `[DECISION NEEDED]` The replacement rule for the A1 pins. A minimum version
   with a named refusal is the obvious shape. The question is whether the SDK and
   Unity pins become minimums, ranges, or disappear because the shader
   attestation already carries the correctness weight.
3. `[DECISION NEEDED]` Whether AMUSE declares
   `BeforePlugin("com.anatawa12.avatar-optimizer")` or accepts its present
   position after Avatar Optimizer. The present position is an accident of phase
   order, not a decision.
4. `[DECISION NEEDED]` Whether a first release blocks an upload on any refusal.
   The NDMF severity model makes this a one-word choice with a large product
   effect. A refusal is a normal outcome for AMUSE, so `Information` or
   `NonFatal` is the safe default.

## 11. What this note proves and does not prove

Proves, by reading the current tree: every gate, absence, and citation in
sections 4 to 7. Absences were checked by search over the package, and the search
result is recorded with the finding.

Proves, by reading pinned upstream source: the NDMF registration minimum, the
error-report call shape, the component and assembly patterns of both neighbor
tools, and the ordering facts in section 5.7.

Does not prove: the coverage estimate of section 3. It follows from the gates,
and it is `[INFERENCE]`. A measurement on a real corpus would settle it, and the
Census Lab is the correct instrument for that. No such measurement was made here.

Does not prove: the Poiyomi lock timing of A2, the effect of a split on frame
time, or the behavior of two VRChat SDK callbacks that declare the same order.
