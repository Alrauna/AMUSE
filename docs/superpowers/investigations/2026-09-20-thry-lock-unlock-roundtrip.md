# Thry lock and unlock round trip - live characterization

## Status and scope

Investigation record. Recorded 2026-09-20 from editor sessions that ran between 2026-09-19 and 2026-09-20. This note makes no production change. It executes the live two-pin characterization that `2026-09-19-poiyomi-locked-materials-paths.md` names as the prerequisite for the transient-unlock path (path 3) and its consent default. Read together with `2026-09-19-poiyomi-locked-materials-characterization.md`, whose static claims this note verifies and corrects.

Question. Does the Thry lock and unlock round trip execute end to end at both tooling pins? Does restore recover the original material? What does the round trip lose? What does one lock, unlock, or cross-era unlock cost?

Privacy note. Only synthetic assets generated by the harness were used. No private avatars, no Census Lab data, no vendor textures beyond the public packages themselves. All editor work ran in throwaway Unity projects outside this repository. Machine paths appear nowhere in this note.

## 1. Method

Three separate Unity 2022.3.22f1 batchmode sessions, one project per cell, on Apple silicon. The machine's Unity editor version matches this repository's `ProjectSettings/ProjectVersion.txt`.

Package pins, each archive digest verified against the digests recorded in the 2026-09-19 characterization note:

- `com.poiyomi.toon` 9.3.64, embedded Thry editor, called era-1 tooling.
- `com.poiyomi.toon` 10.0.22 plus `com.poiyomi.thryeditor` 2.74.2, called era-2 tooling.
- VRChat SDK Base and Avatars 3.10.5, copied from this repository's own `Packages/` so the lab matches the version this repo develops against. Thry's build callbacks reference VRChat SDK types without version guards, so the SDK is required for the editor code to compile.

The harness created a material from the current `.poiyomi/Poiyomi Toon` shader, set a color, assigned a synthetic banded texture to `_MainTex` with tiling 2 by 3, set the render queue to 3000, enabled one shader keyword directly, and saved the material as an asset. It then snapshotted the material, called `Thry.ThryEditor.ShaderOptimizer.LockMaterials`, snapshotted again, called `UnlockMaterials`, snapshotted a third time, locked once more, and compared states. Snapshots cover every property the material's shader declares, the override tags, the keywords, the render queue, the full serialized blob, and the generated shader file's bytes by SHA-256.

Cells:

- Cell A, era-1 native. Lock, unlock, relock under 9.3.64's embedded tooling.
- Cell B, era-2 native. Lock, unlock, relock under Thry 2.74.2 with toon 10.0.22.
- Cell C, cross-era. The material locked in cell A, copied with its generated shader into the era-2 project, then unlocked by Thry 2.74.2. The 9.3.64 shader assets were imported under `Assets/` with their `.meta` files intact so the original shader GUID resolves, and with all of the 9.3.64 editor C# excluded, because the embedded editor cannot coexist with the standalone 2.74.2 package. The shaders and their includes were untouched.

One harness probe matters for reading the results. The directly enabled keyword (color grading HDR in cells A and C, final pass in cell B) is not paired with its feature toggle property. The lock's behavior on that unpaired keyword is therefore observed but may not represent an inspector-driven lock, which would set the toggle property alongside the keyword.

## 2. The round trip executes at both pins

Every lock and unlock call returned success in every cell. Observed timings for one material, batchmode:

| Operation | Cell A, era-1 | Cell B, era-2 | Cell C, cross-era |
|---|---|---|---|
| Lock | 1442 ms, then 1927 ms | 7244 ms | not applicable |
| Unlock | 621 ms | 270 ms | not applicable |
| Relock | 1215 ms | 4875 ms | not applicable |
| Unlock of the other era's locked material | not applicable | not applicable | 2957 ms |

Restore brought back, in every cell: the original shader by name and GUID, the full declared property table (cell A: 251 floats declared by the locked shader against 3097 after restore), all tested colors, vectors, and declared floats, every texture reference including the lab texture's asset GUID, and the render queue (3000 throughout).

## 3. What the round trip loses

Three losses, all reproduced at both pins.

1. A keyword not paired with its feature toggle is lost permanently. After lock, the unpaired keyword is gone from the material keyword list, and it is also absent from the `OriginalKeywords` tag. Restore restores exactly the tag's set, so the keyword never returns. The seven remaining keywords, including shader-internal ones, survived the full round trip.
2. Tiling and offset of stripped textures are not restored. `_ToonRamp` and `_DistortionFlowTexture` carried tiling 2 by 3 before lock. Both were stripped by the lock, and both came back at 1 by 1. This executes the restore imperfection that the 2026-09-19 source read found at `ShaderOptimizer.cs:2903-2912`. `_MainTex` was not stripped, and its 2 by 3 tiling survived both directions.
3. Unlock leaves stale identity tags. `OriginalShader`, `OriginalShaderGUID`, and `OriginalKeywords` remain on the unlocked material. `AllLockedGUIDS` is removed on unlock. So an unlocked material is recognizable as having been locked, and a lock-signature check must read the lock state float, not the tags alone.

## 4. Generated shader facts, live

- Era-1 generated name: `Hidden/Locked/.poiyomi/Poiyomi Toon/<material GUID>`. Asset at `OptimizedShaders/<material GUID>/Poiyomi Toon.shader` beside the material's folder. Relocking in one session reproduced the same path and byte-identical content. The asset's Unity GUID changed when the asset was deleted and regenerated in a later session, so the generated asset's GUID is not stable across delete cycles.
- Era-2 generated name: `Hidden/Locked/.poiyomi/Poiyomi Toon/<content MD5>`. Asset at `Assets/_LockedShaderCache/poiyomi_Poiyomi Toon/<content MD5>/Poiyomi Toon.shader`. The two locks in cell B produced different content addresses and different bytes, because the unlock residue of the first cycle, the stale tags, changed the content hash input. Era-2 locking is deterministic per input state, but a lock-unlock-lock cycle is not address-stable.
- Era-2 wrote `thry_locked_rename_suffix` set to the cleaned material name, where the hyphen became the hexadecimal text `2D`. Era-1 wrote no rename-suffix tag, confirming the era split.
- Both generated shaders declare a reduced property table. Cell A: 251 of 3097 float properties, 8 of 137 texture properties, with `_MainTex`, `_Color`, and `_ShaderOptimizerEnabled` present and `_Saturation` and `_ToonRamp` absent. Cell B: 340 of 3874 floats, 7 of 146 textures.

## 5. Corrections to the 2026-09-19 notes

The 2026-09-19 notes speak for their date. This section records the live corrections.

1. Characterization section 4 says the generated shader keeps the full Properties block. Live evidence falsifies this for both pins. The generated shader's declared property table is reduced to roughly one tenth of the original, retaining the optimizer toggle, `_MainTex`, `_Color`, and the still-declared live properties.
2. Characterization section 3 says every original property name and value remains readable on the material component. True with a mechanism refinement: the values survive in the material's serialized saved properties, about 2842 float entries on the locked material in cell A, and are readable through the serialized object. The shader-facing typed getters cannot see them, because the generated shader does not declare those names. Any AMUSE reader of locked-material values must read the serialization, not the shader property table.
3. Paths note, path 3: restore fidelity is no longer only a line-by-line source claim. Restore executed successfully at both pins and cross-era in these sessions. The prerequisite the paths note names is discharged for the direct API path.
4. Consequence for the floor path: because unlock leaves stale `OriginalShader*` tags, a locked-Poiyomi signature must require the lock state float equal to 1 together with the name prefix. Tags alone would misclassify unlocked materials.

## 6. Consequences for the transient-unlock path

- The restore dependency of path 3 is live-verified: era-1 locked material, era-2 tooling, original shader present, restore succeeds and rebinds by the pinned GUID. The consent subject can state that restore executed in characterization at both pins and cross-era on 2026-09-19 and 2026-09-20.
- Restore is not perfectly lossless even when it succeeds. The consent subject should also state the observed losses: keywords unpaired with their toggles do not survive a lock cycle, and stripped textures lose tiling and offset. AMUSE's unlock happens on the build copy only, so these losses touch only that copy, but a build-copy unlock followed by Thry's upload re-lock reproduces the same round trip on the shipped avatar.
- The unlock-residue fact matters for cache keys and revalidation. A revalidation fingerprint for path 3 must cover the tag state, because unlock residue changes a later lock's content address and because tag presence alone is not lock evidence.
- Poiyomi issue 64, the silent upload-time lock failure: section 9's probe later reproduced this failure class live on 2026-09-20, with a named trigger. The consent subject should cite that reproduction.

## 9. Follow-up probes, recorded 2026-09-20

Three probes ran after the sections above were written, same harness and pins, all strictly local. The upload-path probe invoked only the SDK's local preprocess callback chain. No upload API, no network call, and no account was used or needed at any point, per the owner's constraint. The lock dialog was suppressed first, because in batchmode the dialog auto-accepts and would open the lock documentation page in a browser.

### Probe 1: keyword paired with its toggle property

The first round trip dropped one keyword. This probe re-ran the round trip with the keyword driven the way the shader intends: `COLOR_GRADING_HDR` is bound to `_MainColorAdjustToggle` through `[ThryToggle(COLOR_GRADING_HDR)]` in the 9.3 shader source, so the probe set the toggle to 1 and enabled the keyword. Result: the keyword survived into the `OriginalKeywords` tag, stayed enabled on the locked material, and came back after unlock. Combined with the lock source, where `FixKeywords` reconciles keywords from property values before locking (`ShaderEditor.cs:1519`), the loss boundary is now precise: keywords whose property state contradicts them are reconciled away at lock time and are unrecoverable; property-consistent keywords survive the full round trip.

### Probe 2: tag-2 rename-animated property

The Thry inspector records animated properties as `<property>Animated` override tags, and the lock reads them (`CollectRenamedProperties`, `ShaderOptimizer.cs:1360-1391`). The probe set `_SaturationAnimated` to 2 with `_Saturation` at 0.37 and locked, at both pins. Results, identical at both pins: the generated shader declares `_Saturation_<suffix>` and no longer declares `_Saturation`; the value 0.37 moved to the suffixed name; the suffix is the cleaned material name, where the hyphen became the hexadecimal text `2D`; and the Animated tag itself is absent after the lock. Unlock restored `_Saturation` at 0.37. This executes the rename mechanism the 2026-09-19 notes had only as a source read, and it corrects their tag list: the `<property>Animated` tags are an inspector-era input to the lock, not tags the lock re-emits.

### Probe 3: the order-100 upload lock, live

The probe invoked `VRCBuildPipelineCallbacks.OnPreprocessAvatar` — the same local static chain the VRCSDK upload calls — on a two-renderer avatar holding one renderer-assigned material and one material reachable only through an Animator clip, under Thry 2.74.2. Two states, both live:

- Descriptor initialized the way the SDK UI does it: the callback locked both materials, including the clip-only one, in 637 ms. The order-100 re-lock that transient unlock depends on is real and works on a well-formed avatar.
- Descriptor with a null `baseAnimationLayers` array, which is what `AddComponent<VRCAvatarDescriptor>` produces without SDK initialization: the callback threw `ArgumentNullException` at `ShaderOptimizer.cs:3220`, the VRCSDK aborted the callback chain with the message that the build was aborted because `LockMaterialsOnUpload` threw, and zero materials were locked. The direct API locked the same materials fine in the same session.

This reproduces the failure class of Poiyomi issue 64, upload-time locks that silently do not happen, with a named root cause: an unguarded dereference of `descriptor.baseAnimationLayers`. One environment note for reproducibility: Thry's upload callbacks only compile when the `VRC_SDK_VRCSDK3` scripting define is present. In a VCC-managed project the VCC resolver applies it; a package-copy lab project must add it by hand.

Consequences for transient unlock: the re-lock dependency is now live-verified as a mechanism, and the consent subject can be strengthened from "issue 64 is unresolved" to "a throwing upload callback skips the lock and aborts the build; one concrete trigger is a descriptor with uninitialized animation layers, reproduced live on 2026-09-20." The path-3 spec gains a falsifier: AMUSE's build-copy handling must never leave the descriptor's `baseAnimationLayers` null, and the revalidation step should verify the upload lock's preconditions where it can see them.
