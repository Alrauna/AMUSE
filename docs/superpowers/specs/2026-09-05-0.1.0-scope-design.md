# v0.1.0 scope — design decisions

Date: 2026-09-05. Basis: a grilling session between the controller and the user.
Companion roadmap: `docs/superpowers/plans/2026-09-05-0.1.0-implementation-roadmap.md`.
Labels: `[SOURCE]` is a fact read in pinned upstream source or in this tree.
`[MEASURED]` is an aggregate from a read-only Census Lab query run in this session.
`[DECISION]` is a choice the user made. `[LIMIT]` is a known instrument or evidence limit.

## 1. The goal

AMUSE v0.1.0 ships alpha separation for common Poiyomi Toon and lilToon
configurations, an avatar-root component that users place to opt in, and plain
English build reports. Anything not covered or not fully understood fails
closed and no-ops at the smallest useful scope.

## 2. Decisions

`[DECISION]` V1 — Trigger. A component on the avatar root gates the whole
pipeline. No component means a total no-op with no report. Settings surface is
presence only: no exclusion list, no toggles. The component follows the
neighbor patterns: runtime assembly, `IEditorOnly`, `DisallowMultipleComponent`,
root placement enforced in inspector and build, HelpURL. UX patterns are taken
from d4rkAvatarOptimizer and AAO: Avatar Optimizer.

`[DECISION]` V2 — Coverage targets. The targets are material configurations
under the existing alpha separation contract. No new transformation type. The
four targets: outlines, transparent, single pass transparency, multipass
transparency. Two appearance bars are part of the definition of "supported":
outline-bearing materials require the AMUSE canonical opaque material to
replicate the source outline pass; a triangle moves only if every pass that
draws it is proven opaque on that triangle.

`[DECISION]` V3 — Texture state widening. A7 states are admitted: anisotropic
levels above 1, trilinear filter, mirror wrap. A8 is admitted: lilToon families
gain the affine `_MainTex_ST` path that Poiyomi already has. A6 stays refused
with a named cause: crunch, DXT1, and the other unadmitted formats.

`[DECISION]` V4 — Attested shader set for 0.1.0: lilToon 2.3.4 and Poiyomi
9.3.64, unlocked forms. Widening to lilToon 2.3.0 through 2.3.3 is a fast
follow inside 0.1.0, cut first if the schedule slips. Evidence: one curated
corpus, three read-only aggregate queries. Sixty-four scenes, seventy avatar
instances, zero query failures. Six avatars carry any Poiyomi material. The
lilToon family holds about ninety-seven percent of the optimizable material
instances; Poiyomi holds the rest. All lilToon materials in the corpus carry
material format revision 45. `[MEASURED]` `[LIMIT]` lilToon migrates materials
on startup, so the revision proves format uniformity, not installed package
distribution. Official download counts are the remaining prevalence signal.

`[DECISION]` V5 — Locked Poiyomi moves to 0.1.1. 0.1.0 refuses locked
materials with a visible, plain English reason. Facts that carry to 0.1.1: the
lock engine is ThryEditor, not d4rk; upload auto-lock runs at VRChat callback
order 100, after every NDMF phase, so PlatformFinish tools see unlocked
materials unless they were locked in project by hand; the locked marker value
is 1; locked shaders are generated forms named `Hidden/Locked/...` with an
`OriginalShader` tag; unlock, mutate, relock is the documented working
pattern; unlocked Thry-lockable shaders are stripped from builds, so any clone
of an unlocked Poiyomi material depends on the order 100 locker or on locked
form handling. `[SOURCE]`

`[DECISION]` V6 — Refusal granularity. Material level unknowns refuse per
material slot, not per renderer. Renderer level unknowns keep renderer scope.
A design investigation gates the implementation; the controller approves the
design before code.

`[DECISION]` V7 — Report channel. NDMF `ErrorReport` is the primary surface.
Messages carry a title, details, and a hint, in plain English, with clickable
per object context. The component inspector shows a compact last build status
and pre build guidance. The NDMF console auto-opens after a build that
reported anything, so a silent no-op becomes impossible for opted-in avatars.

`[DECISION]` V8 — Version consent mechanism. Applies to NDMF, VRChat SDK,
Unity, and the attested shader families. Rules:
- Hard refuse, no dialog: null, unparseable, prerelease, Unity non-`f`
  streams, host versions below the declared floors or outside the declared
  ranges, except majors above the upper bounds.
- Click through every build, no memory: in range but unattested host versions,
  majors beyond the declared bounds, and any unattested version of an attested
  shader family, older or newer, any class. Acceptance means classification
  with the nearest attested version semantics. One consolidated dialog per
  build lists every unattested pair with material counts. Batch mode refuses.
- Plain refusal with report, no dialog: shader families AMUSE does not know.

`[DECISION]` V9 — Ecosystem duties. Generated clones and meshes register
through `ObjectRegistry` and `IAssetSaver`. No ordering declaration against
other plugins. The README documents the d4rk hazard: its non NDMF hook can
merge submeshes that AMUSE appended.

`[DECISION]` V10 — Value policy. A mixed submesh always splits in 0.1.0, and
the report shows it. The split threshold is the 0.1.1 headline, measured on
the corpus.

`[DECISION]` V11 — Release shape. PC only. Android and Quest get a named,
visible refusal. `package.json` moves to 0.1.0. `release.yml` produces the
zip. No VPM listing submission. English only. Apply-on-Play stays refused.

`[DECISION]` V12 — Execution topology. Thirteen slices in five waves, three
worktree lanes, four approval gates. A dirty merge stops its lane and reports;
no autonomous conflict resolution. See the roadmap.
